Plugins, hooks y webhooks

Una guía práctica para extender el CMS y conectar automatizaciones sin romper el contrato de contenido.

PluginsHooksAccionesWebhooksAgentesSeguridad

1. Plugins declarativos

Un plugin es una unidad de extensión con identidad, versión, descripción y estado. Su registro declara qué capacidades aporta sin ejecutar código arbitrario dentro del panel.

Plugin { name: "crm-sync", version: "1.0.0", enabled: true, hooks: [...], actions: [...] }

El ciclo recomendado es: registrar, revisar permisos, activar, probar, observar y desactivar si es necesario. Un plugin desactivado conserva su definición para poder reactivarse sin perder configuración.

2. Hooks: reaccionar a eventos

Los hooks conectan un evento del CMS con una extensión. Son adecuados para reaccionar a cambios: crear una entrada, cambiar su estado, asignar un término, actualizar metadatos o modificar una plantilla.

Hook { name: "after_entry_publish", plugin: "crm-sync", priority: 20, enabled: true }

Buenas prácticas

  • Usa nombres de evento explícitos y payloads pequeños.
  • Haz los handlers idempotentes: el mismo evento no debe duplicar efectos.
  • Define una prioridad solo cuando exista una dependencia real.
  • Desactiva el hook antes de retirar o cambiar el plugin.

3. Acciones: operaciones ejecutables

Una acción representa una operación que un humano, un plugin o un agente puede invocar. Debe tener un nombre estable, una descripción clara y parámetros validables.

Action { name: "sync_entry_to_crm", plugin: "crm-sync", input: { entryId: "string" } }

Las acciones son el punto de control para operaciones con efectos externos. Devuelve siempre un resultado estructurado con estado, identificador de ejecución y mensaje útil para auditoría.

Diferencia rápida: un hook escucha un evento; una acción se invoca para ejecutar una intención.

4. Webhooks e integraciones HTTP

Los webhooks conectan Waypoint con servicios externos como CRM, analítica, automatización o colas. El patrón recomendado es que un hook detecte el evento y una acción prepare el payload para el webhook.

entry.published → hook → action → POST /webhooks/content-published

Contrato recomendado

{ "event": "entry.published", "id": "evt_...", "occurredAt": "2026-08-30T...Z", "entry": { "id": "...", "type": "case_study" } }

Para producción, firma el cuerpo con un secreto compartido, incluye un identificador único de evento y reintenta con backoff. El consumidor debe responder rápido y procesar de forma asíncrona cuando el trabajo sea pesado.

La interfaz actual documenta y registra hooks y acciones declarativas; la entrega HTTP de webhooks debe implementarse detrás de una acción o Worker de integración con sus propios secretos y límites.

5. Uso desde WebMCP

Un agente puede descubrir el registro de plugins, hooks y acciones mediante WebMCP, inspeccionar su estado y ejecutar acciones permitidas. La operación pasa por las mismas validaciones que la UI humana.

await agent.call("run_extension_action", { name: "sync_entry_to_crm", input: { entryId } });

Antes de ejecutar una acción con efectos externos, el agente debe confirmar el alcance, el recurso afectado y si la operación es reversible.

6. Seguridad y operación

  • No guardes API keys en la definición pública del plugin; usa secretos de Cloudflare.
  • Aplica mínimo privilegio y separa acciones de lectura de acciones con efectos.
  • Registra actor, plugin, hook, acción, recurso, resultado y timestamp.
  • Usa límites, timeouts y deduplicación para evitar tormentas de eventos.
  • Prueba primero en un entorno controlado y desactiva extensiones fallidas sin borrar su historial.
